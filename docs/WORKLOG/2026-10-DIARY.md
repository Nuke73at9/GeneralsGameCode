### Tiberium Project: the access violation on exit, found with a crash watch and fixed
The game ends with exit code 0xC0000005 every time a test run quits on the user's PC. Windows recorded nothing about it: no Application Error event, no Windows Error Reporting entry, no crash dump in the user data folder (the last ones are from 22/10). That fits the game's own unhandled-exception filter in `WinMain` (it returns `EXCEPTION_EXECUTE_HANDLER`, so the process ends quietly with the exception's code) with its dump writer already shut down, which happens at the very end of `WinMain`: the fault is after that, in the C runtime's exit (static destructors) or a DLL unloading.
- A crash watch for test runs (`TiberiumTest`, Windows only): from the first test frame a vectored exception handler writes every error exception (codes 0xC..., not C++ exceptions) to `TiberiumCrash.log` in the user data folder, with the module and offset, the address read or written, and on x64 the call stack unwound from the faulting context with the modules' own unwind tables (`RtlLookupFunctionEntry`, `RtlVirtualUnwind`); the PDB installed next to the exe turns the offsets into functions. Plain Win32 file writes, so it still works while the process exits. `TiberiumTest::exitStage()` marks the shutdown steps in the same file: the game loop ended, the engine shut down, `GameMain` returned, the memory manager shut down, leaving `WinMain`, and (an `atexit` hook) the C runtime destroying static objects. Both games' `GameMain` and `WinMain` call it; it does nothing outside a test run (on Linux the steps go to stderr).
- Tried under Wine with a stand-in program whose static destructor writes through a null pointer: the log shows the steps up to "static objects are being destroyed", then the access violation with the faulting function's offset and the stack through the C runtime's exit, the same as Wine's own backtrace.
- On the user's PC it caught it on the first run: after "static objects are being destroyed", an access violation reading 0xFFFFFFFFFFFFFFFF in the static destructor of `AutoPoolClass<MultiListNodeClass,256>::Allocator` (the PDB from the build, read with `llvm-symbolizer`), in `ObjectPoolClass`'s loop that frees its blocks. The bug is in WWLib's `mempool.h` and older than this project: a pool block starts with a link to the next block, a pointer, and the objects were placed at `BlockListHead + 1` with `BlockListHead` a `uint32 *`, so 4 bytes in. On x86 that is the pointer's size; on x64 the first object overlapped the upper half of the 8-byte link, and once its memory was used the link was garbage. A pool that grew past one block (W3D's list nodes do in any real game) crashed when the C runtime destroyed it at exit. The objects now start `sizeof(uint32 *)` in (the same as before on x86; also keeps x64 objects 8-byte aligned). On Linux the game exits cleanly either way.
- On the user's PC with the fix (a full rebuild there, 993 steps): both test runs now end with exit code 0, the crash watch shows every shutdown step and no exception, and the frame times are as before (16.9 ms).

### Fix W3DTreeBuffer null dereference in unitMoved during shell map (Issue #347)
- Investigated SIGSEGV reported in issue #347 where `W3DTreeBuffer::unitMoved` crashed due to a null pointer dereference at offset `0x20` (`m_framesToMoveOutward`) during shell map execution when `OpenContain::redeployOccupants()` relocated occupants.
- Discovered that `W3DTreeBuffer::addTreeType()` returned `0` instead of `-1` when tree models/meshes failed to load. When `m_numTreeTypes == 0`, returning `0` caused `addTree()` to accept `treeType = 0` as valid while leaving `m_treeTypes[0].m_data` uninitialized (null) and registering the tree into the spatial partition `m_areaPartition`.
- Corrected `addTreeType()` to return `-1` on error and guarded `addTree()` against null data pointers.
- Added comprehensive bounds checks (`treeType >= 0 && treeType < m_numTreeTypes`) and null guards for `m_data` across `unitMoved()`, `pushAsideTree()`, `applyTopplingForce()`, `updateTopplingTree()`, `update()`, `updateTreeBuffers()`, and `xfer()`.
